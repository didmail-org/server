# DIDMail Server ヘルプ

組織のメールボックス設定、ノード管理、メールの配信方法を説明します。現行のサーバーとクライアントに基づくガイドです。過去の VC 配信文書は、現在サポートされる機能の有効化手順ではありません。

<a id="overview"></a>

## サーバーの役割

DIDMail Server は暗号化されたメールと添付ファイルを保存します。暗号化と復号はクライアント内で行います。ノードはアクセス確認、保存、配信記録、必要な場合のブロックチェーン取引を担当します。

ARC のログイン ID、メールクライアントのメールボックス DID、サーバーのノードウォレットは別の ID です。管理サイトへのログインだけでは ARC アカウントはメールボックスになりません。個人ウォレットもノードウォレットとは異なります。

同じサーバーのメンバー同士のメールは直接保存されます。封筒、支払い、メール NFT、オンチェーン通知は不要です。外部メールは引き続き NFT 封筒を使います。配信方法はサーバーが自動判定するため、利用者向けの別の送信モード選択はありません。

「メールデータをチェーンに記録しない」とは内部配信についての説明です。過去の ID やステーキング取引はチェーン上に残る場合があります。また、保存容量や帯域などのインフラ費用は運営者が負担します。

<a id="quick-start"></a>

## 組織メールボックスを使い始める

1. 運営者からサーバーの HTTPS endpoint と、その ARC 組織への招待を受け取ります。
2. ARC の招待からログインします。組織 ID は有効な所有者、管理者、メンバーのいずれかである必要があります。ゲストや無効なユーザーにはメンバーメールの資格がありません。
3. 更新済みの DIDMail 拡張機能、React Native または Flutter クライアントで endpoint に接続します。メールボックスを作成または選択し、クライアントの ARC メールボックス連携を完了します。承認前に表示されたアカウントとサーバーを確認してください。
4. クライアントで暗号化受信用キーを登録します。連携済みというだけでは、暗号化メールを受信できるとは限りません。
5. 内部メールの送信者には、取り消されていない有効なネイティブトークンのセルフステークが最低 1 token 必要です。サーバーは読み取りで確認し、メール取引は作成しません。引き出し待ちの取り消し済み残高はこの要件に含みません。
6. 別のメンバーにも同じサーバーへの接続、連携、受信用キー登録を依頼します。通常どおり作成し、送信確定前に実際の内部メール条件と保存期間を確認します。
7. 受信トレイを更新します。「内部メール」と「外部メール」は別タブです。通常の更新でも内部メールを同期します。本文とすべての添付ファイルのダウンロードが完了するまでクライアントを開き、その後バックアップ機能を使ってください。

メンバー配信が有効なノードには、公開済み封筒がなくても接続できます。内部配信の条件を満たさない相手への送信には、利用可能な外部用封筒と、実際の条件の再確認が必要です。

<a id="access"></a>

## ログインと管理ページ

[DIDMail 管理画面](/admin)を開きます。ARC がセッションと役割を確認します。ヘルプは公開ですが、業務データは所有者と管理者に限定されます。メンバーは管理画面ではなくメールクライアントを使います。

- [ノードアカウント](/admin/account)：ノード DID、残高、入金、所有者への送金、Gas 用ステーキング。
- [サーバー](/admin/server)：サービスノード NFT、公開ネットワークでの表示、NFT ステーキング。
- [メンバー](/admin/members)：ARC の状態、連携メールボックス、送信ブロック。
- [封筒](/admin/envelope)と[名刺](/admin/namecard)：テンプレートの作成と公開。
- [ストレージ](/admin/storage)：暗号化メール記録、容量、検索、削除。
- [設定](/admin/attachment)：添付ファイルのポリシーと配信の運用状況。

ARC のアバターメニューにはプラットフォームの Admin Console が表示されることもあります。プラットフォームの組織管理と DIDMail のメール管理は別です。ノード資金の送金、ノードのネイティブトークンの Gas 用ステーキング、取り消し、請求は所有者だけが実行できます。

<a id="node-account"></a>

## ノードウォレットの管理

「ノードアカウント」で入金先のノード DID とネットワークを確認します。アドレスをコピーするか QR コードを読み取り、個人ウォレットから正しいネットワークのトークンを送ります。更新して結果を確認してください。残高を取得できない状態は、残高ゼロの確認ではありません。

入金は利用可能な資金を増やします。Gas 用ステーキングはチェーンの規則に従ってネイティブトークンをロックしますが、封筒料金の支払いやサービスノード NFT の購入にはなりません。メンバー送信者の 1 token 要件は、その送信者自身のウォレットについての確認です。

所有者は、利用可能な資金を承認された所有者アドレスへ送金する前に内容を確認できます。ステーク中の資金は利用可能残高として送金できません。Gas 用ステーキングでは、画面の現在の金額と引き出し待機期間を確認します。取り消すと待機期間が始まり、直ちにトークンが戻るわけではありません。表示された資格を満たしてから請求します。

取引結果が不明な場合は、再試行の前に更新し、元の操作結果を確認します。既存サーバーの更新・復元では元のノードウォレットを保持してください。置き換えると ID が変わり、既存資産や暗号化されたドメインキーにアクセスできなくなる場合があります。

<a id="server-node"></a>

## 非公開 endpoint と公開サービスノード

組織内向けには endpoint を直接配布できます。内部メンバー配信にはサービスノード NFT の購入やステーク、ノード負担のメール NFT は不要です。

公開ネットワークの発見一覧に載せる場合は、「サーバー」で設定済みファクトリを確認し、適切なノード NFT を取得してステークを管理します。公開表示は有効なサービスノード NFT ステークに基づきます。トークン残高、ネイティブトークンの Gas 用ステーク、送信許可リストだけでは代用できません。

公開する endpoint を正しく到達可能な状態に保ちます。購入、追加ステーク、取り消し、請求の承認前に、ネットワーク、資産、現在のチェーン規則を確認してください。公開表示と送信権限は別の判断であり、公開ノードも無権限の送信者を拒否できます。

<a id="members"></a>

## メンバーとメールボックス連携

「メンバー」は設定済み ARC メンバーソースの情報と、ノード内のメールボックス連携を表示します。組織変更後は更新します。ソースには役割に加え、信頼できる有効・無効の状態が必要です。役割名だけでは不十分です。

組織への所属とメールボックス連携は別です。メールボックスを連携していない ARC メンバーは内部メールを利用できません。クライアントの「連携済み」は表示用キャッシュであり、権限そのものではありません。サーバーは送信の受け付け時に状態と連携を再確認します。

クライアントのアカウント連携・取り消し手順で正しいメールボックスを管理します。連携に平文の秘密鍵のアップロードは不要です。任意の暗号化復元には元の復元パスワードが必要で、ノードは復号やパスワード再設定を行えません。ニーモニックだけではランダムに生成した過去のデバイス暗号鍵を復元できない場合があるため、完全な暗号化バックアップを保持してください。

「ブロックされた送信者」で送信制限とメモを管理します。新規送信ではブロックがメンバー資格より優先され、支払っても禁止を回避できません。所属変更や連携取り消しで受け付け済みの配信結果は書き換わりません。ローカルの「連携済み」表示を削除しても、サーバーの連携は取り消されません。

<a id="delivery"></a>

## 内部配信と外部配信

**内部：**双方が同じサーバーの有効で適格な連携済みメンバーで、受信者に有効な受信用キーが必要です。選択済み封筒は外部送信用の候補にとどまり、内部配信では使用も課金もされません。保存期間はノードの内部ポリシーに従います。署名付きオフライン受領証はメッセージ、参加者、サーバー、保存期間を結び付けます。オンチェーン証明書や開封通知ではありません。

**外部：**選択した公開済み NFT 封筒と現在の署名付き見積もりが料金と保存期間を決めます。価格ゼロのメンバー封筒でも、ノードが実際のメール NFT の費用を負担する場合があります。これは内部配信とは異なり、チェーン上に情報が生じます。送信者の料金ゼロはノードの費用ゼロを意味しません。

内部見積もりの後、受け付け前に資格が変わると送信は失敗し、条件の更新が必要です。無料の承認を無断で支払いやオンチェーン公開に変更しません。メンバーソースの障害は「確認不能」であり「非メンバー」ではありません。受け付け後の再試行は同じタスクを返し、配信方式の変更や再課金を行いません。

「配信済み」はサーバー側の配信要件の完了を意味し、受信者の既読や完全なダウンロードを意味しません。内部受信トレイは連携先サーバーから取得し、NFT 通知に依存しません。従来の外部配信は外部受信トレイに表示されます。

<a id="envelopes"></a>

## 封筒の作成と公開

「封筒」でテンプレートを作成し、SVG をプレビューし、価格、保存期間、Public または Members 分類を選択します。分類は作成時に固定されます。別の分類が必要なら新しいテンプレートを作成します。メンバー分類が制限するのは利用できる送信者であり、外部受信者全員に組織への所属を要求するわけではありません。

NFT の作成・取得前に実際のファクトリ料金を確認します。公開するとノードから利用可能になり、公開を取り消すと新規選択を停止します。表示可能な公開済み封筒のうち、メンバーの既定値は Members 分類を優先します。同じ分類では最も古いローカル記録が優先されます。クライアントはほかの表示可能な封筒も選べます。

ゼロ価格のメンバー封筒で外部メール NFT を作る場合、ノードウォレットに十分な資金と Gas 資格が必要です。内部メールは封筒を使いません。既存の NFT 規則で保存期間ゼロは無期限ですが、独立した有限の内部メール保存期間を上書きしません。

<a id="namecards"></a>

## 名刺の作成と公開

「名刺」で SVG をプレビューし、既存の価格・保存期間を設定し、Public または Members 分類を選んで作成・公開します。付属サンプルを使い、必須の `{{contact.name}}` プレースホルダーを残してください。封筒 SVG と名刺 SVG は異なる描画フィールドを使います。

分類は利用資格を決め、作成後は変更できません。公開だけで名刺が送信されるわけではありません。連絡先・名刺交換には別の取引と支払い規則があり、内部メールが無料でも自動的に無料・オフラインにはなりません。支払い済みの処理が止まった場合は、元の準備記録と取引 ID を保持し、重複支払いを承認しないでください。

<a id="storage"></a>

## ストレージ、ダウンロード、バックアップ

「ストレージ」でノードのメール記録を検索・ページ表示し、状態と容量を調べ、操作後に更新します。サーバーは暗号化本文、添付ファイル、運用メタデータを保持します。管理ページは平文メールを読む受信トレイではありません。

サーバー記録の削除は、利用可能なサーバーコンテンツを削除します。対象と保持要件を確認して実行してください。ダウンロード済みクライアントコピーの撤回や、既存チェーン記録の消去はできません。結果が不明な支払い・配信を「修復」する目的でメールを削除しないでください。

クライアントはダウンロードした内容をローカル保存します。本文が読めても、すべての添付ファイルが揃ったとは限りません。未完了の添付は保留状態で再試行でき、1 通の失敗でほかの同期を妨げないようにします。完全な暗号化バックアップと過去の復号キーを保管してください。サーバーの自動移行や、ノードの保存期限後に未バックアップの内容を復元できることは保証しません。

ノードのバックアップには、元のノードウォレット、関係データ、対応する暗号化オブジェクトが必要です。D1 のみのエクスポートは完全な D1/R2 バックアップではありません。保存先をまたぐ整合したスナップショットには書き込み停止が必要で、非公開エクスポートを公開アプリケーションパッケージに含めないでください。

ローカル AFS プレビューでは書き込みを停止し、業務状態、対応するオブジェクト、ポリシーと設定、元のノードウォレットを一緒にバックアップしてください。保持した D1/R2 の元データには、その後の AFS 更新は含まれません。

各ストレージレコードで配信の進行状況と診断を確認できます。支払い確認後、送信者の追加支払いなしでメールNFTの作成を自動再試行します。結果が不明な場合は元の署名済みトランザクションを照会または再送信します。拒否を確認した場合にのみ代替を作成し、拒否された過去のトランザクションIDを保持します。証拠が矛盾する場合は確認のため配信を停止します。削除や再支払いでこの確認を回避しないでください。

<a id="settings"></a>

## 制限と保存期間

「設定」で添付ファイルの既存の制御項目を設定します。添付数、各ファイルサイズ、添付合計サイズ、メール全体の暗号文サイズ制限が併用されます。フィールドの単位を確認してください。大きすぎる下書きは修正してから再送信します。

内部メールには、1 日あたりの件数、累積保存容量、アップロード待ちタスク数の割り当て上限はありません。外部メールの未払いアップロード枠も消費しません。保存期間はデプロイ設定で指定し、既定は 30 日です。「メンバー」ページの追加フォームではありません。メールと添付ファイルのサイズ制限、リクエスト頻度制限、アップロード有効期限は引き続き適用されます。運営者は実際のインフラ容量を監視します。

設定名は次のとおりです。

```text
DMP_INTERNAL_RETENTION_DAYS=30
```

変更は受け付け済み条件に遡って適用されません。編集中にポリシーが変わった場合は更新して確認してから保存します。廃止済みの普通メール・オンチェーン VC 配信を再有効化する設定は、サポート対象ではありません。

<a id="troubleshooting"></a>

## よくある問題

- **管理画面に入れない：**ARC でログインし、このインスタンスが所有者または管理者として認識しているか確認します。ARC 接続障害は接続を修復してください。自己申告の役割や DID では代用できません。
- **連携済みなのに内部送信できない：**双方の現在の所属、取り消されていない連携、受信用キー、送信者の有効なネイティブトークンのセルフステークを確認します。ブロック規則、同じサーバー、互換クライアント版も確認してください。
- **`MEMBERSHIP_UNAVAILABLE` または `GAS_STAKE_UNAVAILABLE`：**確認先を検証できません。運営者の復旧後に再試行します。所属がない、またはステークがゼロである証拠ではありません。
- **`DELIVERY_TERMS_CHANGED` またはポリシー競合：**下書きを保持し、条件を更新して新しい結果を確認します。変更後の配信に以前の支払い承認を流用しないでください。
- **`ENVELOPE_REQUIRED`：**受信者が内部配信の条件を満たしていません。利用可能な外部用封筒を選び料金を確認します。公開済み封筒がなければ運営者に連絡します。
- **メールや添付ファイルのサイズ制限に達した：**下書きを小さくして再試行してください。外部メールの未払いアップロード数の上限に達した場合は、既存の外部アップロードを完了するか期限切れを待ちます。同じ失敗に対して新規アップロードを繰り返さないでください。
- **受け付け済み、処理中、結果不明：**元のタスクを更新し、メッセージ ID と、存在する場合は元の取引ハッシュを保持します。運用画面に照合が必要な項目が出る場合があります。応答タイムアウトだけを理由に再度支払わないでください。
- **本文はあるが添付がない：**ノードの保存期間内にその添付を再試行し、空き容量と接続を確認します。過去の復号秘密鍵がない場合は元のデバイスキーのバックアップが必要で、NFT の再検索では解決しません。

問い合わせにはクライアント版、endpoint、メッセージ ID、エラーコード、時刻を添えてください。秘密鍵、ニーモニック、復元パスワード、セッション Cookie、未編集のメール本文は送らないでください。

<a id="deployment"></a>

## 運営者のセットアップと更新

ARC は自身のプロセス内でプロトコル、署名、タスクサービスを実行し、業務データと暗号化オブジェクトをインスタンス AFS に保存します。従来の Cloudflare Workers ランタイムは廃止済みです。保持した D1/R2 データは過去データの復旧と一度限りの移行専用です。ARC は設定済みの信頼できる連携を通じてログインと組織所属情報を提供します。HTTPS の非公開 endpoint だけで、ネットワーク分離や企業内ネットワークへのデプロイが実現するわけではありません。

1. 公開 HTTPS origin、対象ネットワーク、必須のインスタンス Space、信頼できる ARC 接続を設定します。元のノードウォレットの秘密情報は非公開のインスタンス設定に保存し、公開ノードアドレスを確認します。
2. メンバーメールを提供する前に、インスタンス限定メンバーアダプターとアカウント連携を設定します。認証情報を保護し、有効期限前に更新します。役割だけの一覧を有効状態の検証の代わりにしないでください。
3. `pnpm build` でネイティブパッケージをビルドし、`pnpm start --instance <instance-name>` で実行します。既存環境は明示的にインポートし、新規環境は明示的に初期化します。順序付き SQL スキーマと移行履歴を保持し、ARC インスタンスに D1 実行コマンドを適用したり、既存データを初期化で置き換えたりしないでください。
4. 既存ノードの ID とデータを保持します。隔離環境で試験し、ログイン、所属、受信用キー、内部同期、提供予定の外部配信を検証します。
5. 正しい endpoint と互換クライアントを配布します。定期的な配信回復と期限切れクリーンアップを動作させ、容量と照合待ちタスクを監視します。

このリポジトリで開発する場合は Node.js 24.14 以降を使い、`server/` から実行します。

```sh
pnpm install --frozen-lockfile
pnpm start --instance <instance-name>
```

インストール先のインスタンス名を指定します（この作業環境の既存ローカルインスタンスは `didmail-web` です）。`pnpm start --instance <instance-name>` が表示する ARC URL を開いてアプリを有効化します。ARC のコールド再起動後も再度有効化が必要です。業務操作には設定済みの完全なメール・画面 URL `http://didmail-server.localhost:8788` を使用してください。Workers と外部 workerd 実行器は廃止済みです。インスタンスデータと元のウォレットを保持し、ほかの ARC インスタンスは稼働させたままにしてください。ローカル検証は遠隔本番デプロイの完了を証明しません。
