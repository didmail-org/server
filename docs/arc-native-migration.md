# ARC-native server migration

Status: migration in progress; current work and acceptance focus on local ARC. The existing server remains the Workers implementation described in [runtime and deployment](workers-migration.md). Cloudflare-hosted ARC deployment is deferred. This document sets the target and the evidence required before changing that authority. Audience: server contributors and operators.

## Target and boundaries

DIDMail Server should be distributed as one versioned ARC Blocklet whose instance provides the server's UI, protocol endpoints, authorization, persistent data and operational lifecycle. A hosted ARC operator may provision Cloudflare resources underneath; installing DIDMail should not require each end user to deploy a second business Worker and manually create D1/R2 resources. A separately managed Workers deployment may remain a supported alternative while migration proceeds. A Pages deployment or a successful `arc blocklet check` alone does not establish the target.

ARC documentation describes the [Blocklet manifest](https://www.arcblock.io/en/docs/blocklets/manifest-and-capabilities/), [package/instance boundary](https://www.arcblock.io/en/docs/blocklets/package-and-instance/), [AFS data contract](https://www.arcblock.io/en/docs/blocklets/data-and-afs/) and [Cloudflare runtime](https://www.arcblock.io/en/articles/arc-computer-cloudflare/). These describe capabilities and direction, not proof that an arbitrary custom server module runs on every hosted ARC. The ARC application hosting and distribution services replacing the legacy Launcher and Store were not yet open in the [transition announcement](https://www.arcblock.io/zh/articles/blocklet-server-transition/); their eventual package, installation and resource contracts must be confirmed against the target runtime.

## Verified baseline and gaps

- Current server business entry is [`workers/index.ts`](../workers/index.ts). The ARC [package](../blocklet/blocklet.yaml) mounts a [read-only proxy provider](../blocklet/providers/didmail/index.mjs) for health and attachment configuration, not the business implementation.
- The Worker requires dedicated D1 and R2 bindings, node wallet secrets and scheduled processing. Local ARC preview forwards between distinct ARC and Worker runtimes; that is not evidence of an integrated hosted ARC instance.
- The local CLI inspected for this migration is `arc 2.0.0-beta.74 (49c9125c)`, 2026-10-27. `arc blocklet check server/blocklet` accepts its basic package declaration; a basic package check does not validate hosted backend execution or real instance persistence. The isolated current server build reports `instance: stateless`, consistent with the package not declaring the persistent state that the separate Worker currently uses; this is a packaging gap, not proof that existing data is absent. On the existing `didmail-web` daemon, root `arc afs explain /instance` returned `unknown`, while the Blocklet projection `/blocklets/didmail-arc/instance` reported a claimed local DID Space and read/write/batch capabilities. The projection advertises `ifMatch` in its capability metadata. A single isolated local probe wrote one disposable object, issued two concurrent writes with the same `ifMatch` version, observed one success and one conflict, and removed that object. This bounded result does not establish general concurrency guarantees, session authorization, multi-object transactions or Cloudflare behavior; the local evidence is retained under ignored `artifacts/private/arc-native-research/ifmatch-probe.json`.
- Current source and historical QA results are a compatibility baseline, not acceptance of the new runtime. Preserve them while the ARC-native implementation is built and tested independently.
- An isolated `minimal-app` generated by this CLI passed DSL validation, its named profile check and build. Its generated manifest declares `/instance` required; `--cloud none` staging and `arc deploy --dry-run` passed. A separate temporary generic ARC instance served the Demo page with HTTP 200 and exposed a local read/write instance Space. A single disposable-object concurrency probe produced one success and one conflict; the object was removed and the temporary daemon stopped. This local result does not prove custom business code or storage guarantees on hosted Cloudflare ARC. The ignored demo and outputs are under `artifacts/private/arc-native-research/`.
- The opt-in [`arc-instance-live.test.mjs`](../scripts/arc-instance-live.test.mjs) repeats this local architecture check against a newly scaffolded `minimal-app`: it verifies the required instance, runs four rounds of eight concurrent same-version writes with exactly one winner per round, restarts the isolated daemon, and verifies the winning value and rejection of a stale version. On beta.74 the test passed. It runs from `server/` with `DIDMAIL_ARC_PROVIDER_TEST=1 node --test scripts/arc-instance-live.test.mjs` and deletes only its own temporary instance. This single-daemon test does not prove peer-provider atomicity, multi-object transactions, production reliability, or Cloudflare concurrency semantics.
- A synthetic module provider was loaded by the isolated local daemon and its data was successfully listed and read through the application host's `/api/afs/rpc` endpoint. Earlier root, Blocklet-projection and `/afs` probes did not find it; those paths do not establish whether the application-scoped endpoint works. With the original `target`/`path` declaration and `ops: [list, read]`, anonymous writes were rejected as requiring authentication. This is a bounded local observation, not a complete authorization audit. The beta.74 CLI warned that the older documentation example `module`/`target` is deprecated in favor of `target`/`path`.
- The existing DIDMail read-only proxy provider was copied into an isolated Demo and pointed at a synthetic loopback upstream. On beta.74, application-scoped RPC successfully listed its two resources and read health and attachment configuration; an unknown resource returned HTTP 404. The automated opt-in check [`arc-provider-live.test.mjs`](../scripts/arc-provider-live.test.mjs) runs from `server/` with `DIDMAIL_ARC_PROVIDER_TEST=1 node --test scripts/arc-provider-live.test.mjs`. It creates and removes its own temporary evidence instance; it does not use `didmail-web`. This verifies a proxy against a mock upstream, not ARC-native mail business execution, the real upstream, or hosted Cloudflare support. See the [AFS provider contract](https://www.arcblock.io/en/docs/afs/author-a-provider/) and [AFS over HTTP](https://www.arcblock.io/en/docs/agent-access/afs-over-http/) for the interfaces and access boundary.
- An experimental [native attachment-policy provider](../blocklet/providers/didmail-native/index.mjs) reads and validates public policy from `/instance/didmail/attachment-config.json` through the caller's ARC AFS context, without a Worker or implicit defaults. Missing, inaccessible or malformed policy fails closed. Its update action checks the runtime caller's administrator/owner role and the existing policy version, verifies declared conditional-write features, and writes through the runtime-injected internal AFS root after authorization. Passing the network context directly to that write was tested and refused by ARC's base-path policy. The provider is not mounted in the production package and is not authoritative for the current mail API. The isolated [`arc-native-policy-live.test.mjs`](../scripts/arc-native-policy-live.test.mjs) tests guest and member denial, administrator update, stale version rejection, two concurrent updates, malformed data recovery and restart. Its administrator/member identities use ARC's explicitly enabled test-header facility on the temporary daemon; they are not evidence of real DID-Connect login or production membership authorization. The corresponding [unit tests](../scripts/arc-native-policy.test.mjs) exercise validation and preservation of large decimal prices. The test uses a temporary generic ARC instance, not a second DIDMail development instance; it does not prove cross-daemon concurrency or the existing HTTP API integration.
- The beta.74 installed distribution's `assets/blocklets/collections/README.md` says the Node daemon dynamically imports module mounts while the Cloudflare scope activator skips module-target mounts. Its `assets/blocklets/work-board/blocklet.yaml` repeats that Cloudflare limitation. These are version-specific bundled implementation notes, not an independent test of a hosted deployment or a statement about future ARC releases. They make this local `./providers/...` approach unsuitable as an assumed Cloudflare business execution path until the actual target proves otherwise; investigate supported hosted capabilities or an explicitly supported integration instead.
- On 2026-11-03, an anonymous, read-only `list /` request to the user-suggested public [ArcBlock Community](https://arcblock.community/) application showed an `/instance` whose description names R2 and D1. An anonymous `stat /modules/sandbox` returned `AFS_FORBIDDEN`; that result does not establish whether the mount exists, whether its actions can run, or what a different hosted instance supports. The installed beta.74 `sandbox-mount-fixture` describes a Cloudflare mount-policy test for `sandbox://`, but it contains no compute bundle or public route and does not establish mail-server execution, scheduling, secrets, outbound networking, or transactional storage. Do not use the public community application for mutating tests.
- On 2026-11-03 an isolated `minimal-app` Demo was built and staged with ARC beta.74, then uploaded to a newly created, previously empty [Cloudflare Pages project](https://didmail-arc-cf-demo-20261103.pages.dev/). The `arc blocklet deploy --cloud cf` attempt refused to push because its staging directory had no complete publish baseline; after independently confirming the new project had no deployments, its generated staging tree was uploaded with `wrangler pages deploy`. The remotely fetched `.afs/manifest.json`, `.afs/bundle.json`, `blocklet.dist.json` and page layout matched their local bytes. The Pages root returned HTTP 404 and `POST /api/afs/rpc` returned HTTP 405: this is package hosting, not an executing hosted ARC instance. The project is a synthetic public demo and contains no mail data or credentials. The target hosted runtime and ARC-native server acceptance remain unverified.
- The ARC HTTP transport has been separated into a host-independent [transport](../api/src/runtime/arc-transport.ts); the [Worker adapter](../workers/arc.ts) still supplies its Cloudflare binding or HTTPS origin. The ARC authority response parser is also shared by the existing Node and Worker adapters. These changes do not supply an ARC-native business provider, session authority, or deployment.

- The template-cache consistency policy now lives in [host-independent code](../api/src/runtime/template-cache-core.ts) with atomic pointer and invalidation operations supplied by the [existing Workers adapter](../workers/template-cache-store.ts). An ARC storage adapter has not been implemented or proven.

- Protocol request validation and replay handling now use a [host-independent authentication core](../api/src/runtime/protocol-auth.ts) with an explicitly atomic nonce-consumption contract; the existing [Workers adapter](../workers/protocol-request.ts) retains its D1 implementation. No ARC nonce store is claimed.

- Read-only inspection of the published `@aigne/afs-did-space@1.12.0-beta.5` package found conditional-match checks and subsequent D1 writes in separate portions of the implementation. Whether the complete target runtime provides the atomicity needed under concurrent writers remains unverified; do not infer a defect or a guarantee without a controlled concurrency test on the exact deployed version. This inspected package declares `UNLICENSED`; confirm its distribution and dependency terms before incorporating it. No package source has been copied into DIDMail.

## Required contracts before cutover

1. **Execution and ingress.** Prove how the actual target ARC runtime loads a Blocklet's business provider or executable module, maps the existing HTTP protocol routes and preserves request bodies, headers, streaming and errors. Local provider loading or a static page alone is insufficient. Fail closed on unsupported host capabilities.
2. **Instance data.** Keep package assets immutable and durable mailbox data in a real instance-scoped Space. Determine and verify actual provider support for object sizes, byte fidelity, authorization, concurrency, atomic conditional updates, query/pagination, crash recovery and backups. Do not equate an AFS batch API with an atomic database transaction unless the specific provider guarantees and tests it.
3. **Durable state and payment safety.** Preserve unique message and nonce constraints, idempotent operations, atomic payment lane reservations, lease fencing, original transaction evidence, expiry, and reconciliation. Existing D1 conditional updates and batches in [`dmp-jobs.ts`](../workers/dmp-jobs.ts) and related stores must retain equivalent observable safety. A path-based object store without proven equivalent semantics cannot replace these operations.
4. **Identity and secrets.** Use verified ARC caller and member context for administrator and member authorization. Mailbox signing identity, ARC identity and node identity remain distinct. Prove the target's key custody/signing interface supports the existing node identity and signature preimages; never migrate or regenerate a node key implicitly.
5. **Background work.** Verify hosted scheduling, retries, leases and request lifetime. The manifest may declare `cron`, but a declaration is not proof of execution or delivery guarantees. Duplicate, delayed and interrupted jobs must retain the current safety properties.
6. **Migration and reversibility.** Build a versioned export/import and reconciliation path for metadata, ciphertext, attachments, node identity and task/transaction evidence. Validate on isolated copies, check counts and digests, perform restore drills, and leave existing data and runtime recoverable until acceptance.
7. **Public distribution.** Verify package discovery, installation, upgrades, permissions, custom domains, resource provisioning and backup/restore on the actual hosted ARC when available. Do not infer future Store or Launcher APIs from the retired services.

## Work sequence

1. Inventory existing protocol routes, storage operations, signing, scheduled work and deployment/configuration dependencies. Keep their exact compatibility requirements and historical tests.
2. Prove a minimal stateful ARC package with an actual instance Space and executable provider on the local target; record package and runtime versions. Hosted ARC verification is deferred; keep its capabilities and unsupported cases explicit.
3. Introduce host-neutral ports around business operations incrementally. Keep the existing D1/R2 runtime working while adding ARC implementations only where their required semantics have been demonstrated. Do not claim an ARC implementation for an adapter that still calls the external Workers service.
4. Migrate one non-financial vertical slice through the real ARC package and instance, including authorization, persistence and restart recovery. Expand to encrypted storage and delivery only after transactional and security contracts are established.
5. Migrate scheduling, payment/idempotency and recovery using capability-specific implementations and failure-injection tests; preserve the existing route and protocol contracts.
6. After local implementation and acceptance, revisit hosted deployment only when requested and verify the target runtime's distribution and service contracts.

## Acceptance and regression

Create a new ARC-native test baseline once the execution and storage target is proven. Map every implemented server feature and role to the new local and hosted environments. Re-run relevant protocol vectors, unit and integration tests, browser flows, unauthorized access, concurrent writes, duplicate requests, interrupted operations, restart, export/restore and actual encrypted delivery. Record unsupported host features as blocked with evidence. Historical tests of a separate Worker or mocked provider remain useful regression evidence but are not ARC-native end-to-end acceptance.
